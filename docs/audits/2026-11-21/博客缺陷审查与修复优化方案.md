## 2. 已确认缺陷与修复要求

### D01 · 一言在途请求写入旧节点，恢复后的新栏停留在加载状态

- 位置：[hitokoto-universal.user.js:303](../../../public/downloads/hitokoto-universal.user.js#L303)，重点为 307、310、324–348、404–406 行。
- 根因：`isLoading` 是全局锁，发起请求时捕获 `bar`。SPA 删除该节点后，观察器创建新栏，但再次获取句子的请求被锁拦截；原请求成功、失败或超时都仍更新捕获的旧节点。
- 触发：关闭自动刷新（refreshInterval=0）→ 发起延迟请求 → 响应前移除一言栏 → 自动创建新栏 → 原请求结束。新栏可能持续显示加载，直到用户主动点击。开启自动刷新时也可能要等待下一轮。
- 已有证据：从原脚本提取 `fetchHitokoto`，在 Node 内存桩中复现成功、网络失败和超时三种回调，三种情况下新栏均保持 `new loading`。这是核心逻辑复现，尚非真实 Tampermonkey 端到端测试。
- 修复：建立请求代际/节点生命周期约束。回调更新前重新取得当前可见节点并检查启用状态；恢复节点时使它获得缓存结果或有效请求。停用、切换站点规则和重建节点时使旧请求失效；若支持取消则中止旧请求。避免简单移除锁后引入重复请求和旧响应覆盖。
- 验收：自动刷新为 0，分别延迟成功、失败、超时响应；期间删除并恢复栏，新栏均进入明确的结果或错误态。停用后到达的旧响应不得重新创建栏，重复恢复不得产生无界请求。

### D02 · 一言 SPA 观察器生命周期不完整

- 位置：[hitokoto-universal.user.js:397](../../../public/downloads/hitokoto-universal.user.js#L397) 的 setupSPAWatcher；[同文件:748](../../../public/downloads/hitokoto-universal.user.js#L748) 的 applyConfigChange；[同文件:803](../../../public/downloads/hitokoto-universal.user.js#L803) 的启动逻辑。
- 情况 A：观察器只绑定原 `document.body` 的子节点变化。整体替换 body 的操作发生在其父节点，原观察器不能感知，也不会绑定新 body。
- 情况 B：初始关闭或不符合站点规则时，启动函数提前返回；后续启用虽创建栏，却没有补调 setupSPAWatcher，因而删除后无法自动恢复。
- 已有证据：原函数执行桩显示 body 替换后观察目标仍为旧对象；单独执行启用路径时，setupSPAWatcher 调用次数为 0。产品说明中明确宣传 SPA 恢复，见[一言.md:33](../../../src/content/works/一言.md#L33)。
- 修复：由统一的启用/停用生命周期管理观察器和定时器。必要时在稳定父节点上观察 body 更替，再绑定当前 body；启用时幂等初始化，停用时断开。不要为了恢复一个顶层栏而无条件观察整棵 DOM 子树。
- 验收：覆盖初始禁用后启用、白名单切换后启用、整体替换 body、同一 body 删除栏及重复开关；均能恢复且不存在重复观察器或定时器。与 D01 一起回归。

### D03 · 一言配置保存未经过与加载一致的校验

- 位置：[hitokoto-universal.user.js:68](../../../public/downloads/hitokoto-universal.user.js#L68) 的 validateConfig；[同文件:717](../../../public/downloads/hitokoto-universal.user.js#L717) 的保存回调，重点第 729、742 行。
- 根因：加载时 refreshInterval 只接受 0–3600；保存时直接 parseInt 并写入。输入框 min/max 不能替代普通点击回调内的有效性检查。
- 触发：输入 -1 或 3601 后保存。当前页面采用非法值，重新加载却恢复默认值 30 秒。-1 在当前页面停止定时刷新，重载后又恢复刷新，用户难以预期。
- 已有证据：原 validateConfig 执行结果为 -1→30、3601→30；边界 0→0、3600→3600。保存路径源码未调用 validateConfig 或 reportValidity。
- 修复：保存前检查输入有效性，向用户显示范围提示；用一个规范化配置对象同时更新内存与持久化。避免“静默改为默认值”造成误解；对整数、空值和非有限数给出明确策略。
- 验收：-1、3601 被阻止并提示；0、3600 可以保存且重载后保持一致；空值、非整数及重置默认值路径均符合明确规则。

### D04 · 搜索关键词高亮对比度不足

- 位置：[search.astro:220](../../../src/pages/search.astro#L220)；悬停背景见[同文件:210](../../../src/pages/search.astro#L210)；颜色变量见[global.css:11](../../../src/styles/global.css#L11)。
- 根因：高亮前景使用 accent，背景又叠加 18% 的同一颜色，降低亮度差。标题、摘要和标签均为普通字号，应按普通文字检查。

| 主题/状态 | 由源码颜色计算的对比度 | 判断基线 |
| --- | --- | --- |
| 浅色默认 | 4.398:1 | 低于 4.5:1 |
| 浅色悬停 | 4.064:1 | 低于 4.5:1 |
| 深色默认 | 4.508:1 | 数值刚过线，余量很小 |
| 深色悬停 | 4.079:1 | 低于 4.5:1 |

- 修复：为 mark 定义独立主题配色，或保留可读的正文前景，用背景/字重表达高亮；保持默认与悬停两种底色下都可读。不要只调全局 accent，避免连带改变导航、按钮和文章链接。
- 验收：两主题 × 默认/悬停四种组合全部至少达到 4.5:1；用真实浏览器确认 computed style 和透明背景合成。数值依据 WCAG 相对亮度与 sRGB 透明叠加计算，页面背景还可能有细微纹理，需渲染复核并留安全余量。
- 参考：W3C WCAG 2.2 的 1.4.3（Contrast Minimum）。外部参考地址见第 8 节；本次外部正文抓取受限，未把检索摘要当成页面测试结果。

### D05 · 文章正文内联链接只靠颜色识别

- 位置：[global.css:42](../../../src/styles/global.css#L42) 全局移除链接下划线，正文未恢复；现有触发实例为[一言.md:18](../../../src/content/works/一言.md#L18) 中的 Hitokoto（一言）链接。
- 证据：链接 accent 与相邻正文 ink 的对比度，浅色为 2.298:1、深色为 2.363:1；默认没有下划线等非颜色提示。两者均低于通过颜色差异区分内联链接的 3:1 参考条件。键盘聚焦时的轮廓不能代替默认阅读状态的辨识。
- 修复：仅对 `.prose a` 恢复持续可见的下划线，并设置适当偏移；保留已有焦点轮廓。不要给所有卡片和导航统一加下划线。
- 验收：两主题、未悬停且未聚焦时，文章正文链接仍有非颜色提示；键盘可访问且焦点清楚。另以浏览器验证实际样式级联。
- 参考：WCAG 1.4.1（Use of Color）及技术 G183。3:1 不是所有链接均须单独满足的通用门槛；持续下划线可直接解决本问题。

## 3. 工程风险与治理方案

### R01 · 依赖树存在审计告警，但需区分实际暴露面

位置：[package.json:12](../../../package.json#L12)、[package-lock.json](../../../package-lock.json)。本次 npm audit 返回非零码 1，原因是发现风险，并非命令执行故障。原始 JSON 已保存：总计 11 个被报告包，critical 1、high 8、moderate 1、low 1。其统计对象是依赖包，不是独立公告数量，也不是已验证可利用的线上漏洞数量。

| 暴露面 | 当前证据 | 处理方式 |
| --- | --- | --- |
| 静态 GitHub Pages 页面 | Astro 构建为 static，工作流上传 dist | 没有证据说明服务器端公告能直接攻击线上静态站点 |
| 本地开发服务器 | 使用旧版 Astro/Vite/esbuild 依赖 | 优先排查开发服务器相关公告；避免向不可信网络暴露开发服务 |
| 构建、内容与图像处理链 | 审计报告涉及 Astro、sharp、js-yaml 等 | 按公告触发条件核对是否处理不可信输入，不执行攻击样本 |
| 当前未使用或未确认的 SSR/服务端功能 | 报告包含服务端相关公告 | 标注不适用或待确认，不能将包严重性直接当成站点严重性 |

执行方案：

1. 为原始审计中的公告逐项建立“依赖路径、触发条件、项目是否使用、缓解措施、修复版本”表，先处理可达的高风险路径。
2. 在独立升级分支评估 Astro 和相关依赖的兼容版本；本次审计给出的 Astro 修复候选为 7.4.13，是工具候选而非已验证的升级建议，也不声称是最新版本。package.json 的 ^4.16.0 不会自动跨主版本升级。
3. 核对 Astro 跨版本迁移说明、内容集合 API、Node 支持范围和构建产物差异；重新锁定依赖并执行 npm ci、构建、内容与交互回归。不要在主分支直接运行 npm audit fix --force。
4. 升级后重新审计；对剩余项记录适用性、负责人和复查日期。目标是清除未缓解且可达的 high/critical 风险，而非用一次绿色统计替代分析。

### R02 · 发布流程只有构建，没有行为或产物门禁

位置：[deploy.yml:3](../../../.github/workflows/deploy.yml#L3)、[同文件:30](../../../.github/workflows/deploy.yml#L30)、[package.json:6](../../../package.json#L6)。当前工作流仅在 main 推送或手工触发后 npm ci、构建并部署；未见 pull_request 校验、类型检查、交互回归、XML/JSON 与内部路径检查。构建成功不会执行用户脚本的这些异常路径，本次 D01–D05 仍可随正常构建发布。

修复方案：增加 PR 校验工作流，保留现有部署流程；依次执行依赖安装、非交互式类型检查、生产构建、产物校验和少量高价值浏览器用例。为类型检查显式加入所需开发依赖和脚本，避免 CI 首次运行时等待安装确认。优先覆盖请求节点恢复、启用生命周期和搜索/目录/返回路径，不用大量与实现逐行对应的测试堆数量。

验收：故意引入脚本语法错误、缺失站内文件、损坏 XML 或已修复缺陷的回归时，PR 检查失败；全部通过后才可发布。当前审查脚本是诊断快照，复现缺陷会记录 reproduced=true，不会使退出码失败；正式门禁需改成修复后行为的断言并接入 CI，不能原样当作“测试全部通过”的依据。

### R03 · 本地与 CI 的运行环境没有形成一致约定

位置：[deploy.yml:24](../../../.github/workflows/deploy.yml#L24) 固定 node-version:20；本次本地构建为 Node v24.19.0；[package.json](../../../package.json) 未声明 engines，也未见项目级运行时版本文件。

这是可复现性风险，**未证实 CI 当前构建失败**。另外应核对 Node 20 官方生命周期，但本次官方正文抓取受网络限制，本文不把未经直接复核的终止日期写成已确认问题。

修复：结合目标 Astro 版本选择仍获支持的 Node LTS，统一 CI 和本地约定，补充 engines 与版本文件，并在 README 写明安装、构建和预览命令。先在与当前 CI 相同的 Node 20 环境做一次基线，再测试升级后的目标版本，以区分原有兼容问题与升级引入的问题。

验收：干净检出在约定版本上 npm ci、构建、验证可重复；不支持的 Node 版本得到明确提示。完成版本升级后更新本报告基线与依赖审计。

## 4. 内容、SEO、性能与体验优化

本节均为优化建议或条件风险，不额外计入上述 5 项确认缺陷。

### 4.1 内容上线策略优先于增加功能

当前 13 条内容中 12 条标为 demo，作者简介也处于演示状态；页面已有演示说明，这是正确的透明提示，不应删除提示来伪装真实经历。若目标是正式个人博客，应逐条替换为经作者确认的内容后再调整 demo 开关。若目标仍是主题演示站，应继续保留说明。

[content-utils.ts:22](../../../src/content-utils.ts#L22) 返回全部内容；[sitemap.xml.js:6](../../../src/pages/sitemap.xml.js#L6) 和 [rss.xml.js](../../../src/pages/rss.xml.js) 未据 demo 统一过滤。是否让演示内容进入 sitemap、RSS 和搜索索引应形成明确政策。建议正式站按发布状态集中过滤；演示站则保留标识，并按站点目的决定是否索引。不要擅自删除 12 条内容，或默认把“演示”当成错误。

### 4.2 SEO 与分享元数据

- [BaseLayout.astro:33](../../../src/layouts/BaseLayout.astro#L33) 对所有页面输出 og:type=website；文章页可按页面类型传入 article，并补充有真实内容支撑的发布时间、修订时间和分享图。现有 canonical、description、WebSite/BlogPosting JSON-LD 已存在，不应重建整套布局。
- 对搜索结果页、演示内容与空标签页制定索引策略。搜索和标签 URL 使用查询参数，canonical 指向其基础路径；这可以是有意策略，不在缺乏搜索需求数据时认定为错误。若标签需要成为自然搜索入口，再建设静态标签页与分页。
- 迁移站点地址时集中维护 site/domain/下载链接。当前[一言.md:11](../../../src/content/works/一言.md#L11) 的下载地址固定指向生产站；仅当分支预览需要下载本次构建版本时才构成错配风险。若有意只分发生产版，则保留并说明。
- XML 已做本地结构复核；仍需在实际部署上确认 /robots.txt、/sitemap.xml、/rss.xml 的状态码、类型及站点地址一致性。404 状态码必须通过部署验证，不能仅因存在 404.html 就认为已正确返回 404。

### 4.3 性能优化按数据触发

当前索引 gzip 约 13 KB、合并客户端 JS gzip 约 3.3 KB，没有证据支持立即引入更复杂的搜索服务或框架重构。

- 先采集浏览器基线：移动网络下的首页、长文章、搜索结果，关注 LCP、INP、CLS、请求失败和字体切换。当前采用远程 Google Fonts，必须评估目标网络区域的可用性、回退字体和布局变化；不能据 CDN 域名推断已经变慢。
- 列表目前把全部卡片写入 HTML，再由客户端显示每页 10 条（ContentList.astro:30）。13 条总内容规模下不构成已证实性能故障；增长后可改为构建时分页，提供可直接访问的分页 URL 和更完整的无 JavaScript 回退。
- 搜索目前在客户端遍历索引并一次渲染全部命中。先设置性能预算，超过约定预算才做结果分页、索引分片或 Web Worker。建议初始预算：搜索索引 gzip 不超过 100 KB；这是项目建议值，不是行业强制标准。
- 保留书卷式视觉风格、深浅主题、现有卡片和内容层级；本次问题不需要重做设计系统。

### 4.4 需要补测的体验场景

真实浏览器测试至少包括 320/375/768/1440 CSS px、200% 缩放、横屏短视口、键盘菜单与 Escape、目录锚点、浏览器前进后退、列表滚动恢复、搜索超时/重试、减少动态效果偏好、无 JavaScript 阅读路径。它们是待测试清单，不表示全部有缺陷，也不表示已通过。

## 7. 复核方式与文件说明

从项目根目录执行：

```bash
npm ci
npm run build
node docs/audits/2026-11-21/verify-blog.mjs
npm audit --json
```

npm ci 会按锁文件安装依赖；本次实际构建使用工作区现有依赖，未重新执行 npm ci，也未在 CI 的 Node 20 环境复建。npm audit 发现告警时退出码 1 属预期；复核时应保存带日期的新结果，不要把旧快照当作最新数据库状态。诊断脚本会覆盖同目录 verification.json；建议在新日期目录保留下一轮基线。

- `博客缺陷审查与修复优化方案.md`：可检索、可进版本控制的正文。
- `博客缺陷审查与修复优化方案.docx`：同正文的 Word 阅读版。
- `verify-blog.mjs`：读取本地构建产物和原函数，检查语法/路径并复现核心问题；只写审查目录的验证结果。
- `verification.json`：本次本地验证快照，包含测量值和复现输出。
- `npm-audit.json`：本次依赖审计原始输出。
- `build-report.py` 与 `document-validation.json`：Word 生成脚本及内容/结构、XML 核查结果。
